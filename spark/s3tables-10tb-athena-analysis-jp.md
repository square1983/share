# Athena 方案の制限とデータ量評価

Athena UNLOAD を使って S3 Tables からデータを読み出し、顧客に配信する場合のタイムアウト上限と現実的なデータ処理量の分析。

## 一、Athena 主要タイムアウトとハード制限

| 制限項目 | デフォルト値 | 提額可能上限 | 備考 |
|---------|------------|------------|------|
| **DML クエリタイムアウト**（SELECT/UNLOAD/CTAS/INSERT） | **30 分** | Service Quota 申請で **180 分** まで | 提額にはサポートチケット必要 |
| **DDL クエリタイムアウト** | 600 分（10 時間） | — | CREATE/ALTER 等 |
| **DML 同時実行数** | **25** | 100+ まで提額可 | 並列 UNLOAD で利用 |
| **DDL 同時実行数** | 5 | 提額可 | — |
| **クエリ文字列長** | 262,144 bytes（256 KB） | — | 巨大な IN 句で衝突 |
| **結果セットサイズ（コンソール）** | 先頭 1000 行表示 | — | UNLOAD は対象外 |
| **UNLOAD 単一ファイルサイズ** | ハード制限なし | — | データ分布で決まる |
| **Workgroup データスキャン上限** | 設定可能 | — | 暴走スキャン防止 |

## 二、単回 UNLOAD で処理可能なデータ量

### 経験値（30 分タイムアウト下）

| シナリオ | 処理可能な生データ量 | 説明 |
|---------|------------------|------|
| **Iceberg + Parquet + パーティション裁断 + 列裁断** | **1–3 TB** | 最理想ケース |
| **Iceberg + Parquet + フルテーブルスキャン** | **300–800 GB** | パーティションフィルタなし |
| **CSV ソース + フルテーブルスキャン** | **50–150 GB** | 列裁断なし |
| **JSON ソース** | **20–80 GB** | パース負荷大 |
| **複雑な JOIN / 集計** | **100–500 GB** | shuffle で減速 |
| **単純 SELECT + Parquet 書き出し** | **2–5 TB**（理論最大） | 最速ケース |

### スループット影響要因

| 要因 | 影響 |
|------|------|
| ソースデータ形式 | Parquet/ORC > Avro > JSON > CSV |
| パーティション裁断 | 90%+ のスキャン量削減可能 |
| 出力圧縮 | ZSTD/Snappy は無圧縮より高速 |
| 出力ファイル数 | 小ファイル過多はコミット遅延 |
| Engine バージョン | **Athena Engine v3 は v2 より 1.5–3 倍高速** |
| データ偏り | テールタスクで全体遅延 |

## 三、30 分タイムアウト下の単回 UNLOAD スループット推定

```
Athena Engine v3 実測スループット：
- 単純 SELECT + Parquet 出力：~50–80 MB/s（生データ基準）
- 30 分 × 60 MB/s = 108 GB（保守的）
- 30 分 × 80 MB/s = 144 GB（標準）
- 最適ケース（高並列 + 単純クエリ）：1–3 TB 到達可能

180 分に提額時：
- 180 分 × 60 MB/s = 648 GB（保守的）
- 最適ケース：5–10 TB 到達可能（稀）
```

**結論**：

- **デフォルト 30 分タイムアウト**：単回 UNLOAD で安全に処理可能 **≤ 100–500 GB**
- **180 分に提額**：単回 UNLOAD で安全に処理可能 **≤ 1–3 TB**
- **3TB 超**：複数クエリへの分割必須

## 四、10TB シナリオでの Athena 実用方案

### 方案 A：パーティション単位の複数 UNLOAD

```sql
-- dt パーティションありで 10TB が 30 日に分散と仮定
-- 1 日 ~330 GB、UNLOAD 30 分以内に完了

UNLOAD (SELECT * FROM sales_iceberg WHERE dt = '2026-05-01')
TO 's3://delivery/jobs/<job_id>/dt=2026-05-01/'
WITH (format='PARQUET', compression='SNAPPY');

UNLOAD (SELECT * FROM sales_iceberg WHERE dt = '2026-05-02')
TO 's3://delivery/jobs/<job_id>/dt=2026-05-02/'
WITH (format='PARQUET', compression='SNAPPY');

-- ...30 回繰り返し
```

**オーケストレーション方式**：

- Step Functions ループ
- Lambda スケジューリング
- またはローカルスクリプト + boto3

**並行性**：デフォルト 25 DML 並列 → 25 パーティション同時実行可能

- 30 パーティション → 実質 2 バッチ、各 ~15 分
- **理論総所要時間 30–40 分**

### 方案 B：hash bucket 分割

```sql
-- パーティション列なしの場合
UNLOAD (
  SELECT * FROM sales_iceberg
  WHERE MOD(ABS(FROM_BIG_ENDIAN_64(XXHASH64(CAST(id AS VARBINARY)))), 50) = 0
)
TO 's3://delivery/jobs/<job_id>/bucket=00/'
WITH (format='PARQUET');

-- ...50 回繰り返し（各 bucket ~200 GB）
```

⚠️ 欠点：各 UNLOAD で全テーブルスキャンして hash 計算、**スキャンコスト = 50 × 10TB = 500TB × $5/TB = $2500**

## 五、Athena 方案 vs Glue Job 方案 比較

| 観点 | Athena UNLOAD | Glue Job |
|------|--------------|---------|
| **タイムアウト上限** | 30 分（提額 180 分） | 48 時間 |
| **単回データ量** | < 500 GB（デフォルト）/ < 3 TB（提額） | **上限なし** |
| **10TB 処理方法** | 30+ 回のクエリに分割必須 | 単回で可能 |
| **インフラ** | **運用ゼロ** | Worker 設定必要 |
| **料金モデル** | $5/TB スキャン | $0.44/DPU-hour |
| **10TB コスト** | **~$50（スキャン費）** | ~$200–400 |
| **並行能力** | 25（100 まで提額可） | 数十 worker 並列 |
| **再開機構** | 外部で成功した UNLOAD を記録必要 | 設計に組み込み |
| **柔軟性** | SQL 限定（UDF / 複雑変換不可） | Spark で任意コード |
| **コールドスタート** | 秒単位 | 1–2 分 |
| **データ形式** | Parquet/ORC/JSON/Avro/CSV | 任意 |
| **データマスキング** | SQL 式 | Spark UDF で柔軟 |
| **暗号化** | SSE-S3/KMS 対応 | 同上 |
| **エラー分離** | 単一クエリ失敗は該当バッチのみ影響 | Job 失敗は全体に影響 |

## 六、Athena 方案の実際の失敗パターン

| 失敗 | 症状 | 対応 |
|------|------|------|
| **クエリタイムアウト** | 30 分到達で強制終了 | より細かい粒度に分割 |
| **結果ファイル数超過** | UNLOAD で書き出すファイル過多でコミット遅延 | `bucketed_by` で並列度制御 |
| **メタデータキャッシュ** | ADD PARTITION 直後にクエリで見えない | `MSCK REPAIR TABLE` または待機 |
| **Service Quota スロットリング** | 並行数超過 | キュー待ちまたは並行度低下 |
| **データ偏り** | 単一 worker がスタック | Athena 制御不可、クエリ分割のみ |
| **リソース不足** | "Query exhausted resources" | SQL 最適化またはクエリ分割 |

## 七、10TB シナリオの最終推奨

### Athena が適する ✅

- **明確なパーティション列あり**（日付など）
- **各パーティション < 500 GB**
- チームが SQL に精通、Spark 運用したくない
- 一回限り配信（高速再実行不要）
- **総スキャン量制御可能**（重複スキャン回避）

### Athena が不適切 ❌

- パーティション列も主キーもない → 分割困難
- 単一パーティション > 1–2 TB → 提額しても耐えられない
- 複雑な変換 / UDF 必要
- 厳密な chunk 単位 checkpoint 必要

### 実際の選定推奨

| シナリオ | 推奨 |
|---------|------|
| 10TB を日付パーティション、1 日 < 500GB | **Athena UNLOAD + Step Functions 並列** |
| 10TB が単一パーティションまたは無分区 | **Glue Job**（Athena では分割不可） |
| 10TB でデータ変換/マスキング必要 | **Glue Job** |
| 10TB 一回限り配信、パーティション均等 | Athena（コスト 4–8 倍安） |
| 10TB 頻繁配信、高速復旧必要 | **Glue Job + DynamoDB checkpoint** |

## 八、ハイブリッド方案（10TB 推奨）

```
Step Functions オーケストレーション：
1. Lambda：Iceberg $partitions をスキャン、全パーティションリスト化
2. Map State（並行 25）：
   - 各パーティションに Athena UNLOAD 1 つ
   - 失敗パーティションを DynamoDB に記録（軽量 checkpoint）
3. Lambda：全パーティション成功確認、失敗分をリトライ
4. Lambda：manifest.json 生成
5. SNS で顧客通知
```

**利点**：

- 純 Glue より 50% 単純
- 純 Athena より安全（失敗リトライ機構あり）
- コスト最低（~$50–80 スキャン費）
- 自然並列（25 並列）
- **総所要時間 30 分–2 時間**（Glue 6–10 時間より遥かに速い）

## 九、一文まとめ

> **Athena はデフォルト 30 分タイムアウト下、単回 UNLOAD で 100–500GB を安全処理、180 分に提額で 1–3TB まで可能；10TB はパーティション単位で複数クエリに分割し Step Functions で並列実行必須、コストは Glue 方案の 1/5–1/8 だが失敗処理粒度は粗い。**

## 十、決定フロー（簡易判断）

```
パーティション列はあるか？
├── No → Glue Job 推奨
└── Yes
    └── 最大パーティション < 500GB か？
        ├── Yes → Athena + Step Functions 推奨（最安）
        └── No → 最大パーティション < 3TB か？
            ├── Yes → Athena（180 分提額）+ Step Functions
            └── No → Glue Job 推奨
```
