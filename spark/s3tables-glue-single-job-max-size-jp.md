# Glue Job Spark SQL 単一実行での最大処理データ量

「分割しない」= 1 つの Glue Job 内で 1 つの Spark アプリケーションが全データを処理する場合の上限を、AWS 各コンポーネントの制限を総合的に分析する。

## 一、結論サマリー

| シナリオ | 安全に処理可能 | 限界 | 不可能 |
|---------|--------------|------|--------|
| **複雑な変換なし**（読み込み + Parquet 書き出し） | **~20 TB** | **50–100 TB** | > 100 TB |
| **JOIN/集計あり**（中程度の shuffle） | **~5 TB** | **20–30 TB** | > 30 TB |
| **複雑な複数 JOIN/Window 関数** | **~1 TB** | **5–10 TB** | > 10 TB |

> **「快適に処理できる」 = 20 TB 以下**、**「限界」 = 50 TB 前後**、**それ以上は分割必須**。

## 二、コンポーネント別制限の分析

### 1. Glue Job タイムアウト

| 項目 | 値 | 影響 |
|------|-----|------|
| **最大タイムアウト** | **7 日（10,080 分）** | これが絶対上限 |
| 実用タイムアウト | 24–48 時間 | これを超えると運用上問題 |
| 30 worker × G.2X で 10TB | 6–10 時間 | 余裕あり |
| 同設定で 100TB | 60–100 時間（線形換算） | 48 時間超過、危険 |
| 同設定で 1PB | 600–1000 時間 | **7 日上限を超過、不可能** |

**結論**：時間制約のみなら理論上 ~5 PB だが、線形にスケールしない（後述の shuffle 問題）。

### 2. DPU クォータ

| 項目 | デフォルト | 提額後 |
|------|----------|-------|
| **アカウント DPU 上限** | 100 DPU | 500–1000 DPU（要申請） |
| G.2X worker 数（100 DPU） | 50 | 250–500 |
| G.8X worker 数（100 DPU） | 12 | 62–125 |
| スループット（100 DPU、G.2X） | ~10 GB/s（生データ） | — |
| スループット（500 DPU、G.2X） | ~50 GB/s（生データ） | — |

**結論**：500 DPU 提額で 7 日間 = 理論最大 ~30 PB 処理可能（ただし他制約あり）。

### 3. Spark 単一アプリの実用限界

| 制約 | 影響 |
|------|------|
| **Driver メモリ** | Driver = G.2X の 32GB、タスク数 100 万超で OOM リスク |
| **Task 数の限界** | 実用上 100 万 task まで、それ以上は Driver 負荷大 |
| **Partition サイズ** | 256MB 推奨、100TB / 256MB = 400,000 partition |
| **Shuffle ファイル数** | shuffle 大きいほど Driver メンテナンスがネック |
| **Catalyst プランナー** | 巨大プランで遅延 |

**結論**：単一 Spark アプリの実用限界は **100 TB 前後**、それ以上は別 Job に分割推奨。

### 4. Shuffle と Worker ディスク

| Worker タイプ | ディスク | 30 worker 合計 |
|--------------|--------|-------------|
| G.1X | 64 GB | 1.9 TB |
| G.2X | 128 GB | 3.8 TB |
| G.4X | 256 GB | 7.7 TB |
| G.8X | 512 GB | 15.4 TB |

**シナリオ別 shuffle 量推定**：

| ETL 処理内容 | shuffle 量 / 生データ | 10TB データ時 shuffle 量 |
|------------|--------------------|---------------------|
| 単純読み込み + 書き出し | 0%（shuffle なし） | 0 GB |
| 単純 GROUP BY | 50% | 5 TB |
| 中規模 JOIN | 100% | 10 TB |
| 複数 JOIN + Window 関数 | 200–300% | 20–30 TB |

**結論**：

- 単純 ETL：100TB でもディスクは問題なし
- JOIN あり：30TB あたりが G.2X × 30 の限界、G.4X 必要
- 複雑処理：10TB 超えたら大型 Worker 必須

### 5. S3 書き出しのボトルネック

| 制限 | 数値 | 100TB ETL での影響 |
|------|-----|------------------|
| 単一オブジェクト | 5 TB | Parquet 1 ファイル 512MB なので影響なし |
| 単一プレフィックス PUT | 3,500/秒 | 100TB / 512MB = 200,000 ファイル、hash 分散必須 |
| Multipart アップロード | 最大 10,000 パート/ファイル | 単一ファイル 50TB まで対応（実用範囲外） |
| Multipart パートサイズ | 5MB–5GB | Spark 自動制御 |
| S3 結果整合性 | Strong consistency | 影響なし |

**結論**：100 TB でもファイル数 20 万程度、hash プレフィックス分散すれば書き出し律速にはならない。

### 6. Iceberg ソース読み取り

| 制限 | 影響 |
|------|------|
| Manifest list サイズ | 巨大テーブルで Driver 読み込み時間 |
| データファイル数 | 100 万ファイル超で planning 遅延 |
| Snapshot メタデータ | 通常問題なし |
| Predicate pushdown | パーティション/列裁断で大幅にスキャン削減可 |

**結論**：S3 Tables 側は通常ボトルネックにならない、PB 級まで耐える。

### 7. ネットワーク

| 経路 | 帯域 | 制約 |
|------|-----|------|
| Glue → S3（Gateway Endpoint） | EC2 帯域に依存 | G.2X = 10 Gbps クラス、ボトルネックにならない |
| Glue → DynamoDB（Gateway） | 同上 | — |
| NAT Gateway 経由 | 45 Gbps | 50 worker 並列でもギリギリ可能 |

**結論**：Gateway Endpoint 使用なら 100 TB でも問題なし。

### 8. KMS

| 制約 | 影響 |
|------|------|
| KMS RPS | 5,500–10,000/秒 | Bucket Key なしだと 100TB で確実に上限到達 |
| Bucket Key | 99% 削減 | 必ず有効化、PB 級でも余裕 |

**結論**：Bucket Key 有効化で実質無制限。

### 9. CloudWatch Logs

| 制限 | 値 | 影響 |
|------|-----|------|
| 取り込み速度 | 5 MB/s | 大量 worker で詳細ログ出力時に詰まる |
| ログ保持 | 設定可能 | コスト要因 |

**結論**：大規模 Job では log level を INFO 以下に下げる必要あり。

## 三、実例：規模別 Worker 構成

### 10 TB（快適ゾーン）

```
Worker: G.2X × 30
DPU 合計: 60
時間: 6–10 時間
Shuffle 容量: 3.8 TB（GROUP BY 程度なら可）
出力ファイル数: ~20,000
リスク: 低
```

### 30 TB（推奨上限）

```
Worker: G.2X × 50  または  G.4X × 30
DPU 合計: 100–120
時間: 10–18 時間
Shuffle 容量: 6.4–7.7 TB
出力ファイル数: ~60,000
リスク: 中（複雑変換は危険）
```

### 50 TB（限界ゾーン）

```
Worker: G.4X × 50  または  G.8X × 30
DPU 合計: 200–240（要提額）
時間: 18–30 時間
Shuffle 容量: 12.8–15.4 TB
出力ファイル数: ~100,000
リスク: 高（OOM、shuffle 失敗の可能性）
推奨: 2–5 個に分割
```

### 100 TB（理論的上限）

```
Worker: G.8X × 60
DPU 合計: 480（要提額）
時間: 36–60 時間
Shuffle 容量: 30 TB（複雑処理では不足）
出力ファイル数: ~200,000
リスク: 非常に高
推奨: 必ず分割実行
```

### 300 TB 以上

```
単一 Job では非実用的
- Job タイムアウト 7 日に迫る
- Spark Driver 負荷限界
- Shuffle disk 不足
- 失敗時の再実行コスト過大

必須分割
```

## 四、ボトルネック早見表

| データ量 | 主要ボトルネック | 解決策 |
|---------|---------------|--------|
| < 10 TB | なし | 標準構成で OK |
| 10–30 TB | Shuffle ディスク | G.4X 以上 |
| 30–100 TB | DPU クォータ + Shuffle | 提額 + 大型 Worker |
| 100–300 TB | Spark Driver + Job タイムアウト | 分割実行必須 |
| > 300 TB | Job タイムアウト | 必ず分割 |

## 五、データ量別の最適選択

| データ量 | 推奨アプローチ |
|---------|-------------|
| < 1 TB | Athena UNLOAD 単発 |
| 1–10 TB | Glue Job 単一実行（簡素方案） |
| 10–30 TB | Glue Job 単一実行（再開機構あり） |
| **30–100 TB** | **Glue Job 分割（パーティション/日付単位）+ 再開機構** |
| 100 TB–1 PB | Glue Job 分割 + DynamoDB checkpoint + 並列実行 |
| > 1 PB | EMR Serverless / EMR on EC2 + 専用基盤検討 |

## 六、判断フローチャート

```
データ量は？
├── < 10 TB → 単一 Job、デフォルト構成 OK
├── 10–30 TB → 単一 Job、G.4X 推奨
├── 30–100 TB → 単一 Job 可能だが分割推奨
│   ├── 単純 ETL → G.8X × 30、DPU 提額
│   └── 複雑変換 → 必ず分割
└── > 100 TB → 必ず分割
```

## 七、一文まとめ

> **単純な ETL（読み取り + Parquet 書き出し）なら理論上 100 TB まで単一 Glue Job で処理可能だが、shuffle を伴う処理では 30 TB 前後が実用限界、複雑な変換を含むと 5–10 TB で分割を検討すべき。10TB は快適ゾーン、30TB が推奨上限、それ以上は分割が前提。**
