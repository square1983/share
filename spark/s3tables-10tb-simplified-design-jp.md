# 簡素化方案：再開機構なしの全量再実行

「失敗時は最初からやり直す」を許容する場合、設計を大幅に簡素化できる。ただし **コスト** と **適用範囲** を理解した上で判断する必要がある。

## 一、コスト評価（許容可能か事前に確認）

| 観点 | 再開機構あり | 全量再実行 |
|------|------------|----------|
| 失敗コスト | 残り部分（例：10%）の再実行 | **100% 再実行** |
| 単回最長所要時間 | 6–10 時間 | 6–10 時間 |
| 失敗時の無駄 | ~30 分 | **6–10 時間** |
| 失敗時の費用 | ~$30 | **~$300** |
| 7–10% 失敗率の累積コスト | ほぼなし | 平均 1 回分多く実行 |

**10TB 規模を 6–10 時間実行する間、以下のいずれかを踏む確率**：

- Spot 回収：~5%
- DynamoDB / S3 スロットリング：~10%
- データ偏りによる OOM：~5%
- Glue サービス揺らぎ：~2%

**累積失敗確率 15–20%**。5 回に 1 回は完全再実行が必要。

## 二、簡素化後のアーキテクチャ

```
┌─────────────┐    ┌──────────────────────────────────┐
│  EventBridge│───▶│   Single Glue Job (Plan+Execute) │
│  /手動トリガ │    │                                   │
└─────────────┘    └──────────────────────────────────┘
                                    │
                                    ▼
                   ┌──────────────────────────────────┐
                   │  S3 Delivery Bucket               │
                   │  (job_id ディレクトリを overwrite)│
                   └──────────────────────────────────┘
```

**3 Job → 1 Job**、**DynamoDB 不要**、**Step Functions 不要**（または極簡版のみ）。

## 三、削除可能な要素

| コンポーネント | 必要性 |
|--------------|--------|
| ❌ DynamoDB Checkpoint テーブル | **完全削除** |
| ❌ GSI（status-index） | 不要 |
| ❌ リース機構（lease） | 不要 |
| ❌ 条件付き書き込み（ConditionExpression） | 不要 |
| ❌ `_tmp` → 正式パス rename | ディレクトリ全体 overwrite で代替 |
| ❌ Plan / Execute / Verify の 3 Job 分割 | 1 Job に統合 |
| ❌ Step Functions の複雑な State Machine | 任意；「起動+通知」のみで可 |
| ❌ Chunk レベルの状態管理 | Spark が内部処理 |
| ❌ Worker 間の協調ロジック | Spark スケジューラが自然に処理 |
| ⚠️ Snapshot ID ロック | **推奨維持**（一貫性のため） |
| ⚠️ Manifest 生成 | **必須維持**（顧客検証用） |
| ⚠️ 出力パス overwrite | 必須 |

## 四、簡素化方案のコア設計

### 1. 単一 Glue Job のフロー

```
1. 起動時に snapshot_id を記録（一貫性のため）
2. Spark が Iceberg テーブルを FOR VERSION AS OF <snapshot_id> で読む
3. repartition で並列度とファイルサイズを制御
4. write.mode("overwrite") → s3://delivery/<job_id>/data/
5. 書き込み完了後 manifest.json 生成
6. SNS で顧客に通知
```

### 2. 冪等上書き戦略

```
パス設計：s3://delivery/<job_id>/data/
- 同じ job_id で再実行 → ディレクトリ全体を overwrite
- または毎回新 job_id → 顧客は最新成功版を取得
```

### 3. Spark コード一段で完結

```python
df = spark.read.format("iceberg") \
        .option("snapshot-id", snapshot_id) \
        .load("s3tablesbucket.poc_ns.sales")

df.repartition(2000) \
  .write.mode("overwrite") \
  .option("compression", "zstd") \
  .parquet(f"s3://delivery/{job_id}/data/")
```

## 五、維持すべき重要設計

### 1. Snapshot ID ロック（強く推奨）

- 再実行時に異なるバージョンを読むのを防ぐ
- 再開機構なしでも **一貫性は依然として重要**
- そうしないと顧客が毎回異なるデータを受け取る可能性

### 2. Overwrite モード（必須）

- Spark `mode("overwrite")` は旧ファイルを削除してから書き込む
- ただし S3 はトランザクションなし、**削除と書き込みの間に顧客が空ディレクトリを見る可能性**
- 緩和策：job_id でパスをバージョン管理、書き込み完了後に "latest" ポインタを更新

### 3. Manifest ファイル（強く推奨）

- 顧客が完全性を検証する必要あり
- manifest なしでは全データを取得したか判断不可

### 4. 失敗検知（必須）

- Job 失敗時は明確なアラート必須（CloudWatch + SNS）
- 「半製品」を顧客がダウンロードしないようにする
- `_SUCCESS` マーカー + Lambda トリガー通知

## 六、新しい失敗処理ロジック

| 失敗シナリオ | 簡素化方案の処理 |
|------------|-----------------|
| Worker 消失 | Spark が自動的に task リトライ、上限超過で Job 全体失敗 |
| OOM | Job 失敗 → Worker 拡大で再実行 |
| DynamoDB スロットリング | 該当なし |
| S3 503 | Spark/S3A が自動リトライ、失敗継続で Job 失敗・再実行 |
| Snapshot 期限切れ | 再実行時に新 snapshot をロック（データ変化を受容） |
| 途中クラッシュ | 半製品は `<job_id>` パス下、再実行時に overwrite でクリーンアップ |
| 顧客が半製品取得 | **`_SUCCESS` マーカー + manifest で保護** |

## 七、簡素化方案 vs 完全方案 の使い分け

### ✅ 簡素化方案が適する場面

- データ量 **< 1TB**（単回再実行コスト許容範囲）
- Job 時間 < 2 時間（失敗確率低）
- 一回限り / 低頻度配信（毎日実行ではない）
- チームの技術蓄積が限られる、運用リソース不足
- POC / MVP 段階
- 失敗コスト（金額+時間） < 複雑さコスト

### ❌ 簡素化方案が不適切

- データ量 **> 5TB**（再実行コスト過大）
- Job 時間 > 4 時間（失敗確率高）
- SLA 厳格、当日配信必須
- 複数顧客並行、リソース逼迫
- 同データを繰り返し増分配信（冪等性必要）

### 💡 折衷方案：粗粒度 checkpoint

chunk 単位ではなく、**パーティション単位**の単純 checkpoint：

- 各パーティション書き込み完了時に S3 に `_PARTITION_DONE_<partition>` マーカー作成
- 再実行時、マーカー存在のパーティションをスキップ
- 完全方案より 70% 簡単、純再実行より 90% 安全
- 1–5TB かつパーティション列ありの場合に適する

## 八、対比マトリクス

| 観点 | 完全方案（再開機構あり） | 簡素化方案（全量再実行） | 折衷（パーティション単位 checkpoint） |
|------|----------------------|----------------------|--------------------------------|
| コード量 | ~1500 行 | **~200 行** | ~500 行 |
| 依存サービス | Glue + DynamoDB + SF + SNS + CW | **Glue + SNS + CW** | Glue + SNS + CW |
| 実装工数 | 3–5 週 | **3–5 日** | 1–2 週 |
| 失敗再実行コスト | 低 | **高** | 中 |
| 適用データ量 | 1TB–PB | **< 1TB** | 1–10TB |
| 適用 Job 時間 | 任意 | **< 2h** | < 6h |
| 運用複雑度 | 高 | **低** | 中 |
| 一貫性保証 | 強 | 中（snapshot lock 依存） | 中 |

## 九、10TB シナリオへの具体的推奨

**純簡素化方案は非推奨**、理由：

- 6–10 時間の Job 失敗 1 回で ~$300 + 1 日無駄
- 累積失敗確率 15–20%、ほぼ確実に踏む
- 顧客が半製品取得するリスク（`_SUCCESS` 保護があっても）

**推奨順位**：

- **第一選択**：再開機構を維持（完全方案）
- **第二選択**：折衷方案（パーティション単位 checkpoint）、10TB を 100–500 パーティション粒度に分割
- **最終手段**：純簡素化方案 + 10TB を事前に 5–10 個の独立 Job に分割して直列実行（人為的分割）

## 十、一文まとめ

> **データ量が大きく Job 時間が長いほど、再開機構の価値は高まる。10TB 規模では節約される「複雑さ」より失敗再実行の「コスト」が大きく、簡素化方案は割に合わない；ただし < 1TB や POC 段階では簡素化方案がより賢明な選択肢となる。**
